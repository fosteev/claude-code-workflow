# Алгоритм работы над задачей

Единая схема для всех проектов. Цель: сильная модель тратится на суждение
(анализ, решения, ревью), печатание уходит исполнителю, ничего не живёт только
в чате. Сквозные правила — `~/.claude/CLAUDE.md` (пример — `CLAUDE.example.md`) (контекст 120k/200k, шум,
модели, git).

```
вход → 1. анализ → 2. маршрут → 3. артефакт → 4. исполнение → 5. приёмка → 6. закрытие
                        │                          ▲              │
            ┌───────────┼───────────┐              └──────────────┘
          сам        промт →      roadmap →        (цикл по этапам L)
          (S)      исполнитель   этапы → исполнители
                      (M)            (L)
```

Цикл замкнут внутри одной Opus-сессии: она анализирует, пишет промт, **сама
запускает Sonnet-исполнителя субагентом**, получает отчёт, **сама зовёт приёмку**,
коммитит и пушит. Пользователь видит анализ, промт и итог приёмки; вмешивается,
если хочет. Скиллы `/plan`, `/plan-review`, `/continue` ассистент вызывает по
ситуации, не по команде.

## 0. Вход

Задача приходит как ключ Jira, ссылка, текст или «продолжаем». Определить проект
(ключ/путь → корневой `CLAUDE.md` воркспейса), прочитать доку проекта; если задача уже
начата — её roadmap, а не чат.

**Ворота перед циклом.** Шаги 1–6 запускаются только при двух условиях сразу:
есть явная просьба делать («сделай», «делаем», «/plan», «возьми в работу») и
задача больше часа. Иначе:

- голый ключ / ссылка / «глянь» — прочитать задачу, три строки сути, оценка
  размера (S/M/L) и вопрос «делаем? каким маршрутом?» — и стоп;
- задача до часа (S: ≤ 3 файлов, ясно) — сделать сразу, без /plan, без четырёх
  пунктов анализа и без исполнителя; итог 1–2 предложения;
- вопрос, обсуждение, «почему так» — ответ, без кода и без плана.

Ошибка в сторону «сделал слишком мало» дешевле, чем roadmap на два репо по одной
ссылке.

## 1. Анализ — сильная модель, 5–15 % усилий

Выход — четыре пункта, в чате, коротко:

1. **Что просят** одной фразой и **DoD**: команда или наблюдаемый факт, по
   которому «готово».
2. **Разведка**: где в коде (файл:строка), что уже есть, что мешает. Больше
   трёх чтений — субагент Explore, в чат только итог.
3. **Позиция**: проблема/альтернатива первой строкой (правило «Позиция»).
   Крупное или спорное — `/devil` до плана.
4. **Класс задачи** по двум осям:
   - **Размер.** S — до часа, ≤ 3 файлов, без плана. M — до полудня, до ~10
     файлов, одна сессия. L — несколько сессий или несколько репо.
   - **Суждение.** «Ясно» — все решения можно принять сейчас, есть эталон
     для копирования. «Неясно» — открытые вопросы к пользователю, незнакомый
     код, эталона нет.

## 2. Маршрут

| | Ясно | Неясно |
|---|---|---|
| **S** | **Сам, здесь.** Промт дороже работы | **Сам, здесь**, но сначала три строки: решение, DoD, что не трогаю |
| **M** | **Промт → исполнитель** (Sonnet-сессия), ревью здесь | **Решить → промт.** Открытые вопросы пользователю одним сообщением, принятые решения и DoD в чате, затем как M/ясно |
| **L** | **Roadmap → сессии.** Файл по `/roadmap`, каждый этап = промт исполнителю | **`/devil` → roadmap с открытыми вопросами → решения с пользователем → L/ясно** |

**Всегда сам, на сильной модели, независимо от размера:** security-sensitive
код; миграции с данными, raw SQL; транзакции и гонки; правки стейта без
smoke-теста; новая вёрстка без прототипа; всё, где план говорит «по аналогии»,
а аналогия неточная. Такой этап внутри L помечается «Opus» в roadmap, остальные
идут исполнителю.

**Исполнитель** — субагент `general-purpose` на `model: sonnet`, запущенный из
этой же сессии в фоне с промтом из шага 3. Его контекст отдельный, в родительскую
сессию возвращается только отчёт. Исполнитель не коммитит, не пушит, не гоняет
миграции — это делает приёмка. Ручная Sonnet-сессия — только когда
пользователь хочет вести исполнителя сам.

**Проверка маршрута:** если Opus-сессия собирается печатать код по уже
принятому плану — это ошибка маршрута; сказать одной строкой и выдать промт.

## 3. Артефакт

- **S:** код и 1–2 предложения итога. Никаких документов.
- **M:** промт исполнителю по шаблону ниже. Промт показать пользователю и в том
  же ответе запустить исполнителя в фоне — пользователь прервёт, если не согласен.
- **L:** roadmap по `/roadmap` плюс на каждый этап: модель и effort, промт
  сессии, «параллельно / последовательно, потому что …». Место — конвенция
  проекта (по умолчанию `docs/roadmap/`).
  Roadmap — источник правды; промты живут в нём, не в чате.

### Шаблон промта исполнителю

```
<Сессия N — <задача> · Модель: sonnet, effort: high · после сессии N-1 | параллельно>

Работаем в <абсолютный путь>. Задача: <одной фразой>. <Что уже есть, доработка или стройка.>

Читай: <roadmap-файл>; <2–4 дока путями>. Правила: <CLAUDE.md проекта>.
Точки входа: <файл:строка — что там>. Эталон для копирования: <файл>.

Уже решено, не переспрашивать: <решения>.

Порядок: 1. <этап> 2. <этап> … — галочки в roadmap по факту проверки.

DoD: <дословно>. Проверка: <команды>.

Не делать: <границы скоупа>; чужие незакоммиченные файлы не трогать; dev-процессы
и dev-миграции не запускать; «заодно улучшить» — нет; вопрос без ответа в
промте — в отчёт, не додумывать.

Не коммитить и не пушить — это сделает приёмка. Последним сообщением — отчёт:
сделано / отклонения от плана / не проверено / открытые вопросы.
```

## 4. Исполнение

- **Исполнитель (субагент):** строго по промту, скоуп не расширяет, галочки по
  факту, вопросы копит в отчёт, не коммитит. Параллельные этапы L — несколько
  агентов в одном вызове; последовательные — следующий стартует после приёмки
  предыдущего. Пока агент работает, родительская сессия ничего не печатает.
- **Приёмка стартует сама:** уведомление о завершении агента → `/plan-review` с
  его отчётом на входе.
- **Сам (S):** правило «Шум», проверка build/lint/tests до ответа, контекст
  120k/200k. Задача выросла из S в M по ходу — остановиться и вернуться к шагу 2.

## 5. Приёмка — сильная модель

Для M и каждого этапа L, в чистой сессии или в плановой:

1. Дифф против плана (`/code-review`): расхождения — починить или записать как
   принятое решение в roadmap.
2. Прогнать проверки из DoD. Красное — чинить здесь, если за один заход; иначе
   остаток в roadmap и в Jira.
3. Что проверяет только пользователь (UI на устройстве, живая база, визуал
   админки) — чеклистом: что открыть, что нажать, что должно быть видно.
4. Исполнитель систематически ошибся или оказался прав против плана — одна
   строка в roadmap/README темы, чтобы следующие промты это учли.

## 6. Закрытие

- Коммит по правилам репо и **push** в той же сессии. Сессия не заканчивается с
  unpushed-коммитами и без причины в чате.
- Jira: статус, комментарий по факту, worklog.
- Roadmap: галочки, баннер, промт следующей сессии актуализирован.
- Memory: только устойчивые факты и договорённости. Незакоммиченное — в git, не
  в memory.
- `/continue`: здесь / новый чат, с промтом.

## Инструменты по шагам

| Шаг | Инструмент |
|---|---|
| 1–2 анализ, маршрут | `/plan` |
| 3 roadmap | `/roadmap` — модель, промт и параллельность на этап |
| 3 промт | шаблон в `/plan` |
| 4 исполнение | субагент `general-purpose`, `model: sonnet`, из `/plan`; вручную — отдельная сессия `claude --model sonnet` |
| 5 приёмка | `/plan-review`; `/code-review` |
| 6 закрытие | `/continue` (с push) |
| 4–5 подряд по roadmap | `/roadmap-run` — автопилот: исполнитель → Opus-приёмка → фиксация на каждый этап, стоп на скоупе/лимите |
