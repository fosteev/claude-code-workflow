# Plan review — приёмка результата исполнителя

Шаг 5 алгоритма `~/.claude/WORKFLOW.md`. Роль: архитектор-ревьюер на сильной модели,
**после** сессии исполнителя по промту из `/plan` или этапу roadmap. Вопрос один:
сделано ли то, что записано в плане, и если иначе — прав исполнитель или план?
Расхождения чинятся здесь, решения записываются, готовое коммитится и пушится,
непроверяемое автоматически отдаётся пользователю чеклистом.

Принцип: **план — источник правды, но не догма.** Отступил и был прав — меняем план и
пишем почему. Отступил и ошибся — чиним код. Отступил молча — самое опасное, ищем
именно это.

## Шаг 1. Найти план и понять, что выполнялось

1. Обычный вход — отчёт субагента-исполнителя, запущенного из `/plan` в этой же
   сессии: промт и план уже в контексте, отчёт пришёл уведомлением. Иначе аргумент —
   путь к roadmap, промт, ключ задачи; без аргумента: `git status --short` и
   `git log -5` в репо проекта, свежие `docs/roadmap*/**.md` с галочками или баннером
   «сессия N сделана».
2. Из плана вытащить: какие этапы должны были быть сделаны, «уже решено», точки входа
   и контракт, DoD и команды проверки, запреты, пометки модели.
3. Отчёт исполнителя («сделано / отклонения / не проверено») — это заявленное;
   проверяем против фактического.

## Шаг 2. Собрать факт

По каждому тронутому репо:

- `git status --short`, `git diff`, `git diff --cached`; untracked — прочитать.
- Исполнитель коммитил — `git log --oneline` с даты плана, `git show --stat`; диф
  коммитов тоже предмет ревью. Сообщения: формат репо, ключ задачи, **нет подписей
  ассистента** — если есть, `--amend` только на незапушенных.
- Следы запретов: чужие файлы не тронуты, dev-миграций и генерации «руками» нет,
  дев-процессы не висят (только смотреть).
- Состояние roadmap: какие `[x]` стоят, что в баннере, что дописано в решения.

Диф читать целиком, чужой код вокруг — точечно (Serena / grep / sed по диапазону),
файлы целиком не читать. Длинный вывод — в лог, в контекст `tail` и `grep`.

## Шаг 3. Сверка: план ↔ факт

Три списка, каждый пункт с `file:line` и ссылкой на пункт плана:

**A. Расхождения** — план говорит X, код делает Y, решения нет. Вердикт на каждое:
*ошибка исполнителя* → чинить (шаг 5); *план был неточен* → править план и промты
следующих сессий, записать «Решение (дата, по итогам сессии N): …» с причиной;
*пропущено* → сделать сейчас, если в пределах пары файлов, иначе чекбокс с пометкой
«не сделано в сессии N».

**B. Решения по ходу** — исполнитель отступил осознанно и упомянул. Проверить, что
решение здравое и как бьёт по остальному плану (контракт, имена, следующие промты).
Записать подробно: что, почему, что отвергли, кого касается.

**C. Галочки без покрытия** — `[x]`, за которым нет теста, команды или факта.
Проверить самому; ложная — снять. Тесты из плана: каждый есть и проверяет заявленное,
а не «вызвался и не упал».

Сюда же — известные грабли проекта (memory, «Риски» roadmap, CLAUDE.md проекта).

## Шаг 4. Ревью кода и проверки

Полный диф — как `/code-review`, но с фокусом плана: корректность, конвенции проекта,
обработка ошибок, содержательность тестов, мёртвый код. Этап с пометкой «ревью Opus»
или диф больше ~300 строк в стейте/вёрстке — два прохода (свой + `/code-review`);
иначе один. Не пересказывать диф, только проблемы.

Проверки — команды из DoD плана и конвенции проекта (build, lint, tests), только
тронутые репо, дев-процессы не запускать. Красное — разобраться, чья ошибка и
чинится ли за один заход, а не «отметить».

## Шаг 5. Починка

- Мелкое (опечатка, забытое поле, неверный мок, недописанный тест) — чинить самому,
  это и есть смысл сильной модели здесь.
- Среднее (логика в одном модуле, тест-кейс с нуля) — чинить, если укладывается в
  сессию ревью; иначе этап «Доводка после ревью сессии N» в roadmap с чекбоксами.
- Не переписывать рабочее из вкусовщины: иначе, но корректно и по конвенциям —
  оставить.
- Архитектурное расхождение, меняющее скоуп или UX — **не чинить молча**: один
  `AskUserQuestion` с рекомендацией до коммита этой части.
- После правок — проверки шага 4 заново.

## Шаг 6. Доки и трекер

Порядок: roadmap → доки проекта → трекер.

1. **Roadmap:** `[x]` только проверенное; баннер — что сделано, что осталось, что ждёт
   пользователя; решения из шага 3B с датой; промты следующих сессий и контракт — по
   реальному коду.
2. **Доки проекта** (ARCHITECTURE, CLAUDE.md проекта, wiki по конвенции) — если
   поменялся контракт или появился долг. Факт о системе, не хроника.
3. **Трекер** по конвенции проекта (Jira/Linear/GitHub Issues — свой скилл или MCP):
   комментарий «Ревью сессии N (дата): принято / исправлено / осталось / проверить
   руками», статус. Поведение видно пользователю (UI, устройство) — статус «на
   проверке», финальное «готово» ставит пользователь; невидимое (контракт, миграция,
   тесты, доки) при закрытом DoD — «готово».
4. Исполнитель систематически ошибся или оказался прав против плана — одна строка в
   README темы / «Риски» roadmap, чтобы следующие промты это учли.

## Шаг 7. Вердикт, коммит, push

По каждому репо отдельно:

| Состояние | Действие |
|---|---|
| Проверки зелёные, расхождений нет или починены, ручной проверки не нужно | **Коммит и push сейчас.** Если исполнитель уже коммитил — отдельный коммит правок |
| Проверки зелёные, но часть подтверждает только пользователь (вёрстка на устройстве, живая база, визуал) | **Не коммитить это репо.** Чеклист пользователю: что открыть, что нажать, что должно быть видно; коммит-сообщение показать, коммит по его «ок» |
| Спорное решение исполнителя (архитектура, скоуп) | Не коммитить затронутое; вопрос пользователю с рекомендацией |
| Красное и не починить за заход | Не коммитить; сказать прямо, что остаётся, остаток в roadmap и трекер |

Коммит по формату репо, без подписей ассистента; push в той же сессии — сессия не
заканчивается с unpushed без причины в ответе. Исполнитель-субагент не коммитит,
поэтому коммит здесь — штатный путь, а не исключение.

## Шаг 8. Ответ

Одним экраном: вердикт по репо (принято / исправлено / отложено), расхождения списком с
`file:line`, что закоммичено и запушено, чеклист пользователю. Если в roadmap есть
следующий этап и его пометка — не «opus» и не «ждёт пользователя», в том же ответе
дописать его промт в roadmap по реальному коду, в чат — путь и три строки резюме, и
запустить исполнителя с указателем на раздел (`Agent`, `model: sonnet`, в фоне); иначе —
сказать, что ждёт. Без пересказа дифа.
