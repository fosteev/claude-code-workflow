# Roadmap — план задачи в файле

Результат — один md-файл, по которому задачу можно вести (и передать другой сессии) без этого чата. Не эссе и не пересказ обсуждения: этапы, чекбоксы, критерии.

## Шаг 1. Задача

Из аргументов или разговора. Если задача не названа — спросить одной строкой. Уточнить только скоуп-развилки, если они реально меняют план; мелочи решать самому и помечать как принятые решения.

## Шаг 2. Разведка перед планом

План по незнакомому коду — фантазия. Перед написанием:

- Посмотреть, есть ли в проекте конвенция роадмапов (`docs/roadmap*`, `*/roadmap/`, шаблоны вроде `_template.md`) — если есть, следовать ей: место, формат, где живут статусы.
- Прочитать ровно те файлы/доки, которых план касается: понять текущее устройство, точки входа, существующие тесты и команды проверки.
- Не переписывать в план то, что и так лежит в доках — ссылаться путями.

## Шаг 3. Куда класть файл

1. Есть конвенция проекта → по ней (например, `docs/roadmap/<номер>-<slug>.md`).
2. Есть `docs/` → `docs/roadmap/<slug>.md`.
3. Иначе → `roadmap-<slug>.md` в корне проекта.

Slug — kebab-case из сути задачи, коротко.

## Шаг 4. Структура файла

```markdown
# <Задача>

> Статус: черновик | в работе | готово · <дата создания>

## Цель
Одним-двумя предложениями: что должно стать правдой, когда всё сделано.

## Контекст и ограничения
Что уже есть, что трогать нельзя, принятые решения (с пометкой, если это
допущение, а не факт). Ссылки на доки/код путями.

## Этапы

### 1. <Название этапа>
Зачем этап и что в него входит — 1–3 предложения.

- [ ] атомарный шаг
- [ ] атомарный шаг

**Готово, когда:** проверяемый критерий + команда проверки, если есть
(`npm run check`, curl, конкретный тест).

**Сессия:** sonnet | opus, effort; параллельно с этапом N / последовательно,
потому что … Промт сессии — в разделе «Промты» ниже.

### 2. …

## Промты сессий
Один промт на сессию-исполнителя по шаблону из скилла `plan` (шаг 3), в fenced-блоке.
Промт — часть плана: правится здесь, а не в чате.

## Риски и открытые вопросы
- что может не сработать и как узнаем раньше, а не позже
- вопросы, требующие решения пользователя — явно

## Порядок работы
Зависимости этапов, что можно параллелить, с чего начинать.
```

## Шаг 5. Правила содержимого

- **Каждый шаг — строка-чекбокс `- [ ]`.** Шаги внутри этапа оформляются только
  списком чекбоксов, не абзацем и не маркированным списком без `[ ]`: по этому файлу
  ведут работу и отмечают прогресс. Подэтап (`#### 5.1`) — тоже со своими чекбоксами.
  В шапке файла указать, что исполнитель отмечает чекбоксы по ходу работы.
- **Чекбокс = атомарное проверяемое действие.** «Сделать бэкенд» — не шаг; шаг — то, что можно закрыть за один присест и проверить.
- **У каждого этапа есть «готово, когда»** с командой или наблюдаемым фактом. Этап без критерия — это надежда, а не этап.
- **Не сочинять факты.** Всё, что не проверено по коду/докам, помечается «допущение: …» — план обязан отличать знание от догадки.
- **Статусы живут в этом файле** (чекбоксы и баннер) и не дублируются в другие места, кроме требуемых конвенцией проекта (индекс роадмапа и т.п.).
- **У каждого этапа — пометка сессии** (модель, effort, параллельность). Критерий —
  сколько суждения остаётся исполнителю: код и контракт даны дословно, есть эталон —
  Sonnet; суждение по ходу неизбежно (стейт без smoke-теста, миграции с данными,
  гонки, вёрстка без прототипа, security, «по аналогии» с неточной аналогией) — Opus.
  Параллельно — только разные репо, зафиксированный контракт, нет генерируемых
  артефактов и общих файлов между этапами; одно репо — всегда последовательно.
- Размер по задаче: маленькой задаче — 3–5 этапов на страницу, не раздувать структуру ради структуры. Для одной сессии раздел «Промты» — один промт.

## Шаг 6. Финал

Создать файл, в ответе — путь к нему и этапы одной строкой каждый. Не пересказывать файл целиком в чат.
