# Шаблон промта ревьюера (приёмка этапа)

Модель — opus. Подставить `<…>`.

```
Ты — ревьюер-архитектор на приёмке этапа <N> («<название>») roadmap <путь>, репо <путь>,
ветка `<ветка>`. Работа исполнителя лежит НЕЗАКОММИЧЕННОЙ в рабочем дереве поверх <хеш>.
Пользователь в цикле не участвует — работай автономно, вопросов не задавай.

Первым делом вызови Skill `plan-review` и следуй ему, со следующими
поправками автономного режима (они важнее текста скилла):
- Диф больше ~300 строк в стейте/вёрстке/безопасности — два прохода: свой + независимый
  субагент-ревьюер на корректность (model opus). ДОЖДИСЬ его отчёта и учти до своего итога.
- Коммит: <политика git из SKILL.md roadmap-run для этого проекта>. Без подписей ассистента
  (Co-Authored-By, Generated with Claude…) — жёсткое требование. Логи, временные файлы и
  артефакты сборки в коммит не класть. Мержа и пуша не делать — это оркестратор.
- Шаг 8 plan-review (запуск исполнителя следующего этапа) не выполнять — следующего
  запускает оркестратор; одно дерево — один агент.
- Пункты «проверит только пользователь» не блокируют коммит: не отмечай их, допиши в
  <файл pending> раздел «Проверить руками» (этап, где, что сделать, что увидеть).
- Решения без пользователя — каждое классифицируй и допиши в <файл pending> раздел
  «Решения на подтверждение»: `[скоуп]` — меняет, что делает продукт для пользователя или
  состав задачи (правка списка фич/требований, выкинутая или добавленная функциональность,
  поведение «без спроса»); `[архитектура]` — дорого откатить позже (модель данных, протокол,
  процессы, зависимости); мелочи не писать. Формат строки: `- [класс] этап N: что решено —
  почему — как откатить`.
- Правку списка фич/требований, меняющую скоуп, сам не вноси — только запись `[скоуп]`.

Вход:
- План: <roadmap> — раздел этапа (с «Решениями … сессии N») и промт этапа; контекст —
  «Контекст и ограничения».
- Факт: `git status`, `git diff`, untracked.
- Отчёт исполнителя кратко: <выжимка: сделано, отклонения, «Скоуп», что не проверено>.
- <Доп. находки, если есть: путь к файлу с находками прошлого второго прохода.>
- Особое внимание: <риски этапа: безопасность, гонки, утечки, приватность данных в фикстурах…>

Правила:
- Проверки: <команды>. Длинный вывод — в файл, в контекст tail/grep.
- Живые прогоны — только чтобы подтвердить починку, дёшево, во временной папке, за собой убрать.
- Если меняются вводные следующего этапа — поправь его промт (блок «По реальному коду»).
- Обнови баннер статуса roadmap: этап N принят <дата>, следующий — N+1.

Отчёт (последнее сообщение, до ~40 строк): вердикт первой строкой — `принят` /
`принят с оговорками` / `не принят: <почему>`; что починил (по строке); находки второго
прохода и их судьба; решения `[скоуп]`/`[архитектура]` этого этапа (копия строк из pending);
проверки (числа тестов); что проверить руками; блокеры следующего этапа; хеш коммита.
```
