# Review Local Changes

Провести ревью локальных незакоммиченных изменений в текущем git-репозитории. Никаких `gh`/`glab` — только локальный git.

## Шаги

1. **Собрать состояние репозитория** — запустить параллельно:
   - `git status` — что изменено, добавлено, не отслеживается
   - `git diff` — unstaged изменения отслеживаемых файлов
   - `git diff --cached` — staged изменения
   - `git rev-parse --abbrev-ref HEAD` — текущая ветка (для контекста)

2. **Прочитать untracked-файлы** — для каждого нового файла из `git status` использовать Read, чтобы увидеть содержимое (его нет в diff).

3. **При необходимости — расширенный контекст**: если диф трогает функции/типы, чьё определение не видно в патче, прочитать соответствующие файлы целиком, чтобы корректно судить о корректности изменений. Не догадываться — читать.

4. **Если изменений нет** — сообщить пользователю и остановиться.

5. **Анализировать и выдать ревью на русском** в следующей структуре:

   ### Обзор
   Что в сумме делают изменения (1–3 предложения).

   ### По файлам
   Для каждого затронутого файла — пункт с путём `file:line` и сутью изменения.

   ### Замечания
   Сгруппировать по серьёзности:
   - **Критично** — баги, сломанная логика, утечки, нарушения безопасности, регрессии.
   - **Важно** — нарушения конвенций проекта (CLAUDE.md), плохая обработка ошибок, потенциальные проблемы производительности, дублирование.
   - **Стиль/мелочи** — именование, форматирование, мелкие улучшения читаемости.

   Каждое замечание: ссылка `file:line`, что не так, как поправить.

   ### Что хорошо
   1–3 пункта про удачные решения (если есть). Не выдумывать ради галочки.

   ### Рекомендация
   Одно из: «готово к коммиту», «нужны правки» (с перечнем критичных), «нужно обсудить» (если есть архитектурный вопрос).

## На что обращать внимание

- **Корректность** — логика, граничные случаи, обработка ошибок.
- **Конвенции проекта** — учесть `CLAUDE.md`/`README.md`/`design-guide.md` в корне репо, если есть. Не нарушать описанные там правила.
- **Безопасность** — секреты в коде, XSS/SQLi/инъекции, небезопасные defaults.
- **Производительность** — лишние ре-рендеры в React, N+1 запросы, тяжёлые операции в hot-path.
- **Покрытие тестами** — если в проекте есть тесты, отметить отсутствие тестов на новую логику. Если тестов в проекте нет — не выдумывать команды и не требовать их.
- **Мёртвый код / TODO / закомментированный код** — флажить.

## Чего не делать

- Не запускать `gh`, `glab` и не обращаться к внешним хостингам.
- Не редактировать файлы — только ревью. Правки — только если пользователь явно попросит после.
- Не пересказывать diff построчно — фокус на проблемах и сути.
- Не выдумывать тесты/линтеры/команды, которых нет в проекте.
